# 性能与资源预算（为什么这套后端能跑在小机器上）

这套自建后端的目标不是「功能对齐 Emby」，而是**在 1~2 核、1~2G 内存的机器上稳定出流**：
扫描不把内存吃满、不把磁盘喂满 fsync、刮削不逐条串行等网络。

> **v2.38.0 追加**：这一版解决的是反方向的同一件事——「写事务里等网络」。扫描 / 维护 / 图片清理
> 的网络与磁盘 IO 全部移出事务，写路径加写锁退避重试（`backend/db_retry.py`），
> 并顺手修掉 4 个资金链路的读-改-写（卡码并发核销 / 退款并发 / 履约缺料 / 两阶段提交）。
> **细节、实测数字与验证命令见 [`docs/performance-transactions.md`](performance-transactions.md)。**
>
> 验证：`python scripts/smoke_test_scan_write_concurrency.py`（CI 会跑）——给扫描器的 IO 出口
> 装上「有没有落在未提交的写事务里」的探针（探针先自证有效），一边全量扫描一边循环打真实的
> 写接口 `POST /api/admin/economy/plans`：写事务里的 IO **0 次**、最长写事务 **约 150ms**、
> 并发写接口中位 **14ms** / 最大 **0.18s**、`database is locked` **0 条**。

> **v2.39.0 追加**：这一版把「`async` 路由里做同步 DB」的**存量清零**——
> `scripts/check_blocking_routes.py` 的基线从 24 条清到 **0 条**（管理 / 用户 / 经济三域的写库
> 整段下放线程池，必须 await 的通知与网络留在事件循环上；人工补单与支付回调共用的
> `economy._fulfill_order` 一并改回同步函数）。
> **逐域改动、口径与验证见 [`docs/performance-blocking-routes.md`](performance-blocking-routes.md)。**
>
> 注意：本文件后面的「二·七」小节与「三、已知瓶颈」里还留着「存量还有 24 / 37 条」的旧说法，
> 它们描述的是当时的状态；**最新状态一律以本节与那份专门文档为准**。

## 一、扫描

| 维度 | 旧实现 | 现在 | 说明 |
| --- | --- | --- | --- |
| 条目查询 | 每个文件 1~3 次（条目 / 剧集 / 季） | 每 `SCAN_BATCH` 个文件一次 | 十万文件：几十万次 → 几百次 |
| 提交（fsync） | 每个文件一次 | 每批一次 | 实测 166 → 5 次；这是「扫一次库把盘拖住」的主因 |
| 探测（ffprobe） | 串行，单文件最长 90 秒超时 | `SCAN_WORKERS` 并行 | 一个坏文件不再拖死整库进度 |
| TMDB 刮削 | 逐条串行等网络 | 同一条目内串行、条目之间并行 | 搜索 → 详情有依赖，所以放在同一个工作线程里 |
| TMDB 调用数 | 每条 1~2 次，无缓存 | 预热与写库共用一份响应缓存 | 不会因为「预热 + 写库各调一次」双倍耗配额 |
| 目录列举 | 每个文件两次（找图 + 找字幕） | 每个目录一次 | 远程挂载上等于每次少两次网络请求 |
| 内存 | 清理阶段把整库条目一次载入 | 游标分批（每批 `SCAN_BATCH`） | 十万级库不再出现内存尖峰 |
| 清理的从属数据 | 删条目时只删条目本身 | 同时清掉媒体流与播放进度/收藏 | 播放进度没有 ORM 级联，旧实现会留下只增不减的孤儿行 |
| 重扫（追新） | 每个文件走完整流程（~4 条 SQL + 1 次提交） | 目录指纹未变就整个跳过 | 2000 文件库：2455 ms → **144 ms**（见「三、已知瓶颈」） |
| 清理候选集 | 遍历该库全部条目 | 先两次计数证明无需清理，退回遍历时每批 5000 条只读 4 列 | 十万条目：2097 ms → **37 ms** |
| 探测子进程优先级 | 与 API 同优先级，和播放抢 CPU/磁盘 | `SCAN_IO_NICE` 只降 ffprobe 子进程 | `nice` 是进程级的，本进程不能降（会连播放一起降） |

可调环境变量：

| 变量 | 默认 | 作用 |
| --- | --- | --- |
| `SCAN_BATCH` | `400` | 每批文件数（批量查库 / 落盘的粒度）。小内存机器可以调小，比如 `100` |
| `SCAN_WORKERS` | `4` | 并行 IO 线程数（探测 / 目录 / TMDB）。核数少就调小，`1` 表示退回串行 |
| `TMDB_API_KEYS` | — | 多密钥轮询（`key1,key2`），一个 key 限额后自动换下一个 |
| `SCAN_INCREMENTAL` | `1` | 目录指纹增量扫描（置 `0` 回到「每次全量处理」的旧行为） |
| `SCAN_CLEANUP_BATCH` | `5000` | 清理阶段每批读多少条目（不碰 IO，批越大越省往返） |
| `SCAN_IO_NICE` | `10` | 探测子进程的 niceness（`0` 关闭）；有 `ionice` 时同时降 IO 优先级 |
| `PROBE_REMOTE_RANGE_BYTES` | `1048576` | 远程探测第一跳的头部窗口（1 MiB）。实测 8 MiB 会触发 ffprobe 的 “File ended prematurely”，调大会变差 |
| `PROBE_REMOTE_TAIL_BYTES` | `2097152` | 第二跳的尾部窗口（2 MiB），只对 moov 在文件尾的 MP4/MOV 生效；与头尾两个请求**并行**发出 |

> 第二跳的判定条件（全部满足才会触发）：第一跳没读出时长 + 容器是 MP4/MOV 系 +
> 文件大于第一跳窗口 + 没有明确的 HTTP 错误。两个 Range 并行发出，落盘的是「头部 + moov」
> 的小文件（1 MiB 出头，与原文件大小无关）。详见 CHANGELOG 的 2.42.16。

## 一·五、扫描队列（v2.27.0）：同一远程挂载串行化

一次线上日志审计的结论：四个媒体库在同一分钟里点「扫描」，四个任务**合法地**同时跑起来——
单个库的互斥只防「同一个库重复扫描」，不防「不同的库同时打同一个远程挂载」。同一个 WebDAV
端点被四个任务反复 PROPFIND，远端延迟被放大、SQLite 被四个写入方争抢，CPU 打满而 `item_count`
长时间是 0。**最小根因修复是「按远程挂载串行化」，不是提高线程数。**

| 机制 | 行为 |
| --- | --- |
| 按挂载串行化 | 一个库扫描期间锁住它要读的远程挂载；引用同一挂载的库排队。只读本机目录的库不受影响 |
| 全局并发上限 | `EMBY_SCAN_MAX_PARALLEL`（默认 2）：扫描是资源大户，不设上限时「多点几下」就能打满机器 |
| 排队是正常状态 | 重复点不报 409（合并并说明原因）；接口写明「在等哪个挂载」；排队可取消，正在跑的不能取消 |
| 远程并发上限 | `MOUNT_REMOTE_CONCURRENCY`（默认 2）：网盘 / WebDAV 在高并发下不会更快；本机目录不吃名额 |
| 遍历线程数 | `SCAN_WALK_WORKERS`（默认 8，2026-10 从 16 降半）：并发是掩盖延迟，不是换吞吐 |
| 前台让路（2026-10-16） | 扫描在批次边界检查 Redis 前台打点（aetrix-api 限流中间件顺手写）；120s 内有用户请求则小睡让路（5s/轮，单次扫描上限 900s）。`SCAN_FOREGROUND_YIELD=0` 可关；Redis 不可用时=旧行为 |
| 一轮只列一次 | 扫描会话期间目录缓存不看 TTL（同一目录被目录指纹 / 字幕 / 预取反复问到） |
| 进度可查 | `Library.scan_progress` 每 `EMBY_SCAN_PROGRESS_FLUSH` 秒落盘：阶段 / 已发现 / 已处理 / 当前目录 |

实测（`scripts/verify_scan_queue_concurrency.py`，同一台机器、同一个假 WebDAV、四个库连点扫描）：

| 指标 | 升级前（`EMBY_SCAN_QUEUE=0`） | 现在 |
| --- | --- | --- |
| 同时在跑的扫描 | **4** | **2**（上限） |
| 同一挂载上任务重叠 | 0.7 s | **0 s**（串行化） |
| 排队可见性 | 无（都显示「扫描中」） | 第几位 + 在等哪个挂载 + 排队时长 |
| 四个库的结果 | 2 个扫描因并发写库互踩失败、条目为 0 | 4 个全部 success，每个远程库都枚举完整个挂载 |
| 墙上时间（60 文件 × 3 库 + 本机库） | 2.2 s | 3.9 s（串行化换稳定性；真实场景里远端延迟被放大，并发通常更慢） |

出问题时看日志（排队决策都记 INFO，不用靠猜）：

```
扫描入队：库「电影」(id=2) 触发=manual；等挂载 [1]；队列长度 1
扫描开始：库「剧集」(id=1) 排队 0.0s；占用挂载 [1]；同时 1 个在跑
扫描结束：库「剧集」(id=1) → success；耗时 1.2s；本轮远程列举 4 次（复用 63）
```

## 二、播放

- **直连优先**：能满足客户端（容器/编码/码率）就 `FileResponse` 直出，用 `Range` 支持拖动；
  只有确实不兼容才起转码，转码是**子进程**，进程退出即回收，不在主进程里堆帧。
- **会话在内存**：播放会话不写热点表，避免每次心跳都产生写入放大。
- **图片本地化**（v2.17.0）：刮削到的海报/背景图落一份到 `EMBY_IMAGE_DIR`，客户端从本服务器
  拿图；缓存被清掉会按需自愈，落不下来退回代理 —— 源站慢/不可达时媒体库封面不再跟着抖。
- **挂载目录列举缓存**（v2.17.0）：`MOUNT_LIST_CACHE_SECONDS`（默认 30 秒，2026-10 从 5 秒上调）内同一目录只问一次
  网盘，扫描与播放共用；失败不缓存、同一目录单飞、内存有上限（`MOUNT_LIST_CACHE_MAX`）。

## 二·五、协议路由的线程模型（v2.13.0）

- **按关注点拆分模块**：协议面原先集中在 `backend/emby_server/api.py`（2100+ 行），现拆成
  `api.py`（系统信息 / 认证 / 列表与详情 / 播放核心）、`media_routes.py`（图片 / 下载 / `hls1`）、
  `compat_routes.py`（会话上报与协议补齐）、`stream_routes.py`（容器变体流 / 原始文件 / 字幕）。
  四个模块把路由注册到**同一个** `emby_router` 上，导入顺序与拆分前的定义顺序逐条一致，
  所以 `mount_routes` / `image_routes` / `session_routes` 的「路径 + 端点名替换」照旧生效。
- **同步 `def` 优先**：路由体内没有 `await` 的一律写成同步 `def`，由 Starlette 线程池执行——
  同步 SQLAlchemy 查询、读盘、远程代理都不会占住事件循环。只有真正需要 `await` 的才写
  `async def`：要 `await request.json()`、`await` 异步响应流（`video_stream` / `video_hls`），
  或者被别的模块 `await` 复用。新加端点时按这个口径选签名。
- **为什么要拆**：文件小，单次改动的 diff 可读、可评审；后续把剩下的异步路由换异步 ORM
  或继续下沉阻塞调用时，改动面是可控的。
- **转码已删除（2026-10-17）**：服务端转码能力（ffmpeg 会话、HLS 切片、中继代理）
  整套下线，播放侧只剩 302 直链（播放器自拉）。上述「`*_async` 变体」约束随转码移除；
  结束会话只标记结束时间，不再有子进程可停。

## 二·六、分类筛选的索引（v2.15.0）

分类值（流派 / 工作室 / 标签 / 发行平台）原先只存在 `emby_items` 的逗号分隔文本列里，
客户端点「类型 / 制作公司」时服务端只能写 `genres ILIKE '%动作%'` —— **前置通配符用不上任何索引**，
等于每次筛选都把整库扫一遍（代价随库大小**线性增长**）。现在由
`emby_item_facets(item_id, kind, value)` 承担：

| 环节 | 做法 |
| --- | --- |
| 写入 | 挂在 SQLAlchemy Session 的 `before_flush` / `after_flush` 上：同一事务里重建这些条目的关联行（先删后插）。扫描器、图片修复、将来任何写入路径都不用手动调；批量 Core 删除走不到事件，由 `prune_orphans` 兜底 |
| 查询 | `MediaItem.id IN (SELECT item_id FROM emby_item_facets WHERE kind=? AND value IN (...))`，走 `(kind, value, item_id)` **覆盖索引**；主查询按主键取条目，文本列上不再有 LIKE |
| 取值菜单 | 一次覆盖索引扫描拿全 kind 的取值（带进程内缓存），分级/年份改成单列 `DISTINCT` |
| 写入细节 | 新条目确实没有旧行，所以**只有分类值变过的老条目**才先删后插；扫描器每批都是新条目，热路径上省掉一次无谓的 DELETE |
| 老库 | 启动维护按 id 水位分批回填（每块提交，可断点继续）；筛选路径也带预算补块（5s 冷却）。**没补完就先退回旧匹配**，结果一样对，不会出现「升级后筛选空白」 |
| 语义 | 关联表侧是「全等，或取值里包含该名字（大小写不敏感）」，与旧 `ILIKE '%x%'` 一致（传 `Action` 照样命中 `Action-Adventure`） |

可调环境变量：`ITEM_FACETS_FILTER_BUDGET`（筛选路径一次补多少条，默认 2000）、
`ITEM_FACETS_BACKFILL_BATCH`（维护回填批大小，默认 2000）、
`ITEM_FACETS_CACHE_TTL`（取值缓存 TTL，默认 600s；扫描/回填会主动失效）。

### 实测数字（10 万条，SQLite，`scripts/benchmark_item_facets.py`）

这是**读多写少**的取舍：省在客户端反复点的读路径，付在条目变化时的写路径。
两头都量过，不要只记住结论：

| 项目 | 旧（逗号文本列） | 新（关联表 + 索引） | 说明 |
| --- | --- | --- | --- |
| 少见取值筛选（命中 20 条） | 19.9 ms | **0.06 ms** | 约 300x；耗时随**命中条数**走，与库总量无关 |
| 常见取值筛选（命中 29% 库） | 21.6 ms | 21.2 ms | **基本持平**：命中三万条时，索引也帮不上忙 |
| 筛选菜单取值 | 153.7 ms | **11.5 ms** | 13x（旧实现还把所有列读回来物化） |
| 扫描写入（ORM 新建 5000 条） | 775 ms | 842 ms | 每条多 13 µs（1.09x） |
| 看护周期 `prune_orphans`（36 万行、无孤儿） | — | 27 ms / 600s | 占 CPU 约 0.004% |
| 每次筛选的常数开销（`ensure_ready` + 取值匹配） | — | 0.8 ms | 取值 5000 个时 1.4 ms（纯内存比较） |
| 老库一次性回填 | — | 1.4 万条/秒 | 10 万条约 7 秒，分批提交、可断点继续 |

结论要诚实：**收益的大头不是「常见取值筛选」**（那本来就只是 20 ms 级的全表扫描），而是
筛选菜单（13x）、合成 Id 反查表（以前每个带 `GenreIds` 的列表请求都扫一遍库）与
**少见取值筛选（约 300x）**；而且旧口径的代价随库增长（50 万条时列表页约 107 ms），
新口径只随命中条数走。反过来，扫描入库多花 9% 的写时间——一次性成本，可以接受。

同一份基准还比过三种写法，**不要**随手改成「更直观」的那种：

| 写法 | 少见取值 | 常见取值 | 结论 |
| --- | --- | --- | --- |
| `id IN (子查询)`（当前实现） | 0.05 ms | 21.2 ms | 最好 |
| `JOIN` + `DISTINCT` | 0.06 ms | 23.2 ms | 常见取值更慢，且多值命中时要额外去重 |
| `EXISTS` 相关子查询 | 43.9 ms | 44.0 ms | 比旧的全表扫描还慢 2x，最差 |

重新量一遍：`python scripts/benchmark_item_facets.py [条目数]`（默认 10 万，只在临时库上跑，
不碰现有数据）。

### 性能护栏（CI 里跑，防止悄悄退化）

`python scripts/benchmark_item_facets.py --guard` 用 2 万条、几秒钟跑完，判定的是**比值**
而不是耗时（比值与机器快慢无关）。门禁的下限取得很保守——真实差距是阈值的几十倍，
只有真的改坏了才会红：

| 护栏 | 下限 / 上限 | 实测（本机） |
| --- | --- | --- |
| 少见取值筛选：关联表 / 全表 LIKE | ≥ 5x | 87x |
| 筛选菜单：覆盖索引 / 读整列 | ≥ 2x | 12x |
| 写入钩子开销（同一批 ORM 新建） | ≤ 3x | 1.15x |
| 看护周期 `prune_orphans` | ≤ 2000 ms | 5 ms |
| 每次筛选的常数开销（`ensure_ready` + 取值匹配） | ≤ 50 ms | 0.8 ms |
| 取值 5000 个时的名称匹配 | ≤ 20 ms | 1.4 ms |
| 回填吞吐 | ≥ 500 条/秒 | 1.4 万条/秒 |
| 两条路径的**条数**一致（常见 / 少见取值） | 相等 | 相等 |

这之前只有「功能正确」的门禁：把索引路径改回全表扫描、或者在写入钩子里塞逐条查询，
依赖都是绿的。

### 升级现场的四项演练（`scripts/smoke_test_item_facets_upgrade.py`）

关联表是**派生数据**，升级上来的老库在回填完成前会同时存在「索引路径」与「降级路径」。
这条测试专门演练开发机上很难自然遇到、但真实升级必经过的场景：

1. **降级口径**：还没回填完时筛选必须完全等于升级前的 `ILIKE '%x%'`（用冷却窗口把路径钉在降级分支上验证）；
2. **回填中途被打断**（进程被杀 / 写库报错）：异常向上冒、已提交的块保留、水位停在**块边界**，
   并且不会被误判成「已能代表全库」；
3. **重启续跑**：换个 Session 接着跑能补齐，幂等，关联行与条目列**逐行一致**（无重复、无遗漏、无孤儿）；
4. **读请求的补块**：一次请求把老库补完但每块不超过预算（实测每块 5/5/5/5/5/5/2 条），
   冷却窗口内的并发请求不重复抢写锁、也不改任何状态。

## 二·七、管理后台按域拆分 + 阻塞路由整改（v2.21.0）

### 为什么先拆 `admin.py`

管理后台原先是一个两千多行的单文件：改一处审计点要在几千行里翻，也没法整体复核。
现在拆成 `admin_core.py`（公共骨架：`admin_router` / `get_current_admin` / `_audit` /
`_generate_code` / `_log_out`）、`admin_auth.py`（登录 / 身份 / 改密）、`admin.py`
（订阅、用户、卡码、公告、工单、求片、操作日志、统计）、`admin_economy.py`
（邀请返利、积分台账、经济设置与统计）。三个模块注册到**同一个** `admin_router`，
导入顺序 = 拆分前的定义顺序（FastAPI 按注册顺序取第一个匹配，顺序变了就是错路由）。

两件必须守住的事（都有验证，不是“看起来没问题”）：

- **端点集合逐条不变**：拆分前后 `@router.<方法>("路径")` 声明都是 391 条，无增无减；
- **注册顺序逐条不变**：管理路由 53 条的顺序与拆分前完全一致。

顺带把「共享骨架」这件事做实：原先 `admin_ops` / `coupons_admin` / `orders_admin` /
`servers` / `realms` / `emby_servers` / `reminders_admin` / `capabilities_admin` 八个模块
都从**那个两千行的 `admin.py`** 里 `import _audit, get_current_admin`，现在统一指向
`admin_core`。`admin_core` 里只留「真的有多个模块在用」的东西。

### 同步 `def` 优先（把 v2.13.0 的口径推行到底）

v2.13.0 已在协议面定了口径：路由体内没有 `await` 的就写同步 `def`，由 Starlette 线程池执行
（FastAPI 对 `async def` 是在事件循环上直接跑的，同步 SQLAlchemy 查询会卡住整个进程）。
这一版把它推行到门户 / 管理 / 经济 / 设置等各处：**一次性把 100 个「体内没有 `await`
的 async 路由」改成同步 `def`**，业务代码一个字没动。现在全站同步 `def` 路由 92 个。

### 两条静态护栏（都是“只许减少，不许增加”）

这类整改有个共同的坑：把 `async def` 改成 `def` 之后，**别处可能还在 `await` 它**
（例如 `coupons_admin.list_coupon_usages` 被 `list_coupon_usages_by_code` 复用、
`api.user_views` 被 `compat_routes` 复用）。编译、导入、类型检查全都看不出来，
只有真打到那个请求才会 `TypeError: object dict can't be used in 'await' expression`。
所以两条都进了 CI：

- `scripts/check_await_consistency.py`：`await f(...)` 里裸名调用的 `f` 若在 `backend/`
  有模块级定义，就必须至少有一个 `async def` 版本。只看裸名（`await obj.f(...)`
  无法靠文本可靠解析，宁可不报也不误报）。
- `scripts/check_blocking_routes.py`：`async def` 路由里出现同步 DB 调用即失败。
  存量记在脚本的 `BASELINE` 里，只减不增：v2.35.0 做掉两条热路径 → 39 条；
  v2.36.0 两条求片链路 + 通知层下放线程池 → 37 条；v2.37.0 探测 / 体检层 13 条 → 24 条；
  **v2.39.0 把剩下的 24 条全部做掉 → 0 条（基线现在是空的）**。口径：只认路由函数体自身、
  以及**体内定义且被直接同步调用**的嵌套函数；被 `run_in_threadpool` / `to_thread`
  下放的嵌套函数放行（本仓库已有此写法，见 `portal_mount_routes.py`）。

护栏最容易的失效方式不是报错，而是**根本不会响**。所以 `scripts/smoke_test_static_guards.py`
（进 CI）拿合成代码树喂这两条护栏，每一条都要求「真实代码树上退出码为 0」+「合成代码树上
必须失败并点名」：

- await 契约：`async` 端点里 `await` 一个纯同步裸名函数 → 必须报；只写点号调用
  （`await obj.f(...)`）不报（口径如此，不误报优先）；
- 阻塞路由：真实代码树上扫描结果与基线**逐条相等**（既没有死条目、也没有漏网）；
  合成树上 `async`+`db.commit` 要报、同步 `def` 不报、不碰库不报、直接调用的嵌套函数要报、
  下放的嵌套函数不报。

### 剩下的阻塞路由：为什么不是机械改 `def`（v2.21.0 时点 41 条 → v2.37.0 时点 24 条 → **v2.39.0 清零**）

`scripts/check_blocking_routes.py` 基线里那 41 条**都有必须 `await` 的东西**：
`notify_admin_event` / `notify_staff_users` / `notify_all_users`（通知推送）、
`probe_and_store` / `refresh_mount_health` / `probe`（网络探测）、`stop_transcodes_for_async`、
`await request.json()`。也试过「只把同步那段拆出来」以外的更省事写法，但它们真正的麻烦在于：

> **那些「必须 await 的东西」自己也**在 `async` 函数里跑同步 SQLAlchemy。

即 `backend/notifications.py` 的 `notify_admin_event` / `notify_staff_users` / `notify_all_users`
内部都有 `db.query` / `db.add` / `db.commit`；`backend/servers.py` 的 `probe_and_store` 同理。
所以这不是 41 个端点的事，而是要连通知层 / 探测层一起改，**不能靠一次机械替换收尾**——
这也是它没有被塞进这一版的原因（改错就是全站通知链路，或者后台操作返回 500）。

v2.36.0 把**通知层**那一半拆掉了：`notify_staff_users` / `notify_all_users` 的落库段
（查人 + 写站内消息 + 提交）整段下放线程池，两个求片端点自己的写库段也一样（见二·九）。
v2.37.0 再把**探测 / 体检层**那一半拆掉：`servers.probe_and_store` 的「读这一行 + 落库」
下放线程池，13 个走它的端点跟着改完（39 → 37 → **24**，见二·一〇）。

下一步的两种修法（按「这个端点有没有必须 await 的东西」选）：

1. 没有必须 `await` 的 → 改同步 `def`。优先，且**一次一个文件**地做；
2. 有 → 拆成「同步核心 + `await run_in_threadpool(核心, db, ...)`」，同时把通知层里的
   同步 DB 段落也拆出去（否则只是把瓶颈挪了一层）。

值得优先动的是**热路径**而不是管理员偶发操作：`compat_routes.session_progress`
（每个正在播放的客户端每 10 秒上报一次）与 `emby_server/api.py::user_views` 两条
**已在 v2.35.0 做掉**（见二·八）；`user.py::create_media_seek` 与
`admin.py::push_media_seek` 两条求片链路**已在 v2.36.0 做掉**（见二·九）；
整条**探测 / 体检链路**（13 条）**已在 v2.37.0 做掉**（见二·一〇）。

（下面这些在 v2.39.0 已全部做掉——逐域改动见 [`docs/performance-blocking-routes.md`](performance-blocking-routes.md)，
这里保留原描述，因为「为什么不是机械改 `def`」这个判断仍然成立。）
剩下 24 条的分布（`scripts/check_blocking_routes.py` 里可读）：`admin.py` 11 条
（公告 / 工单 / 消息 / 订阅与订单，都是管理员偶发操作，且都要 `await` 通知或结算）、
`user.py` 3 条（工单 / 已读）、`emby_server/*` 6 条（115 账号与扫描相关的长任务）、
其余散在 economy / coupons / orders / reminders。它们的共同点仍是二·七 的那句话：
**要动就得连它 await 的那一层一起拆**——下一个自然的批次是「工单 / 站内消息」这一族
（都要 `await` 通知层，而通知层已经拆完了，端点侧只剩自己的那几段同步写）。

## 二·八、后端热路径与稳定性（v2.35.0）

这一版不加功能，只处理两件「用户能感觉到的卡」和两件「跑久了会慢慢变差」的事。
每条都在 `scripts/smoke_test_backend_hot_paths.py` 里量出数字或数出 SQL，不靠“看起来没问题”。

### 热路径一：会话进度上报不再占事件循环

`POST /Sessions/Playing/Progress` 是**全站最热的写路径**：每个正在播放的客户端每 10 秒上报一次，
一次上报要读会话 / 写位置 / 写观看进度（2~3 条 SQL + 1 次提交）。它是 `async def`（要
`await request.json()`），原先这几条同步 SQL 就跑在事件循环上——多路并发播放时，**所有人的其它请求**
都得排在这几次写事务后面。现在路由只负责解析 JSON，整段同步写库下放 `run_in_threadpool`
（`Playing` / `Progress` / `Stopped` 三个端点同样处理）。

`smoke_test_backend_hot_paths.py` 用后台心跳量「事件循环被占住多久」，先自证方法有效
（把同样的同步活儿直接跑在循环上 → 心跳空洞 ≥0.3s），再量改动后的真实路由：

| 场景 | 心跳空洞 | 说明 |
| --- | --- | --- |
| 基线（同步写库跑在循环上） | 0.36 s | 等于那次写事务的耗时 |
| 现在（一次 0.35 s 的慢写走真实路由） | **0.011 s** | 活儿照做（会话与进度都真落库），只是不在循环上 |

### 热路径二：分类菜单端点不再读整列

`/Genres`、`/Studios` 原先**每个请求**都把整库的 `genres` / `studios` 文本列读回来再切分
（十万级库约 190 ms，且随库**线性增长**——客户端每打开一次筛选面板就付一次）。现在走
`emby_item_facets` 的 `(kind, value, item_id)` 覆盖索引（带进程内取值缓存）；老库没回填完
才退回旧口径，取值逐条一致（脚本两边都比过）。同理 `/Items/{id}/Similar` 的流派匹配
也从 `genres ILIKE '%…%'` 换成关联表条件（每开一个详情页就少一次全库扫描）。

### 稳定性一：筛选菜单「扫完就能看见」，但不会每请求重建

筛选菜单取值来自全库，原先只能等 TTL（默认 300 秒）自然过期——刚扫完的片子在客户端的
「类型 / 制片公司」里最长 5 分钟看不到。现在分类值一变（扫描 / 图片修复 / 删条目的**同一个
flush 钩子**，见 `facets.add_change_listener`）就把缓存标成陈旧，下一次「到点」的请求重建。
重建带最小间隔（`EMBY_FILTERS_MIN_REFRESH`，默认 5 秒）：扫描期间每个批次都会触发失效，
十万级库重建一次约 80 ms，不能让它退化成「扫描时每请求一次」（脚本用 SQL 计数证明：
连续 5 次改动 + 5 次请求，相关 DISTINCT 至多 2 条 = 最多重建一次）。

### 稳定性二：库长到几十万行后，查询计划不跟着退化

看护周期（`MAINTENANCE_INTERVAL`）里加了一条 SQLite `PRAGMA optimize`：库从小长到大、
数据分布也变了之后，查询计划不能还按很久以前的统计信息估行数（估错就是全表扫）。
绝大多数时候它什么都不做（毫秒级），只在某张表确实该 `ANALYZE` 时才动手；非 SQLite 直接跳过。
维护周期返回里多一个 `query_plans_optimized` 布尔，便于观测。

可调环境变量：`EMBY_FILTERS_CACHE_TTL`（筛选菜单 TTL，默认 300s）、
`EMBY_FILTERS_MIN_REFRESH`（被标陈旧后的最小重建间隔，默认 5s）。

验证：`python scripts/smoke_test_backend_hot_paths.py`（CI 会跑；v2.36.0 起还覆盖求片 / 通知层）——量出会话上报的事件循环空洞
（基线 0.36s vs 现在 0.011s）、数出菜单请求的 SQL（冷读只有覆盖索引上的 DISTINCT，不读整列）、
并用 SQL 计数证明筛选菜单「改动看得见、但不会每请求重建」。

## 二·九、求片链路与通知层：写库下放线程池（v2.36.0）

二·七 里写过「真正的瓶颈是通知层自己也在 `async` 里写库」。这一版先拆掉通知层，
并把清单上剩下的两条**求片链路**（用户提交 / 后台推送）一起做掉。

| 位置 | 原先 | 现在 |
| --- | --- | --- |
| `notifications.notify_staff_users` | `async` 里查管理员 + 逐条 `db.add` + `commit`，全跑在事件循环上 | 落库段拆成 `_persist_staff_messages`，`await run_in_threadpool(...)`；WebSocket 实时推送仍 await |
| `notifications.notify_all_users` | 同上，且是一次给所有启用用户写几万行 | 拆成 `_persist_broadcast_messages`（自开会话）下放线程池 |
| `user.py::create_media_seek` | 去重 / 额度 / 落库都在 `async` 路由体里 | 拆成 `_create_media_seek_sync` 下放线程池（400 / 409 / 429 语义未变） |
| `admin.py::push_media_seek` | 取件 + 记录结果 + 两次提交 + 审计都在 `async` 路由体里 | 取件与「记录结果 + 审计」各拆成同步函数下放线程池；提交后**返回纯值**，避免回到循环上触发隐式回查 |
| `servers.push_media_seek` | `active_config()` 同步查库留在 `async` 里 | 两次查库改成 `await run_in_threadpool(active_config, ...)` |

验证（`scripts/smoke_test_backend_hot_paths.py` 第 4 节，进 CI）：先自证方法有效
（把站内信落库直接跑在事件循环上 → 心跳空洞 **0.36s**），再让「写站内信慢 0.35 秒」的
真实路由进来提交求片 → 空洞 **0.012s**，同时求片记录与管理员站内消息都真的落库；
后台推送在没有可用 qB 时如实记 `push_status=failed` 并写审计。

阻塞路由基线：39 → **37**（`scripts/check_blocking_routes.py`）。

## 二·一〇、探测 / 体检层：写库下放线程池（v2.37.0）

二·九 收尾时写过「下一个批次按探测层收口」。这一版就是它。

**根在 `backend/servers.py::probe_and_store`。** 它是「保存服务器 / 体检 / 激活 / 节点同步」
四条业务共用的那一段：先 `await probe_server(...)`（真发 HTTP，8 秒超时都可能），
然后**在同一个 `async` 函数里**读这一行、写结论、提交。也就是说一次后台点「测试连接」，
全站（包括别人的播放）就排在那次探测后面；多服部署里「总览」页开着 `live=True`
更是一次串起好几台机器。

这一版的改法就是二·七 里写好的第 2 条修法——**探测（网络）仍 await，同步 DB 整段下放
线程池**，并在两处做了「提交之后不要回读 ORM」的处理：

| 位置 | 原先 | 现在 |
| --- | --- | --- |
| `servers.probe_and_store` | 读行 + 写结论 + `commit` 都在 `async` 体里 | `load()` / `store()` 两个嵌套同步函数交给 `run_in_threadpool`，中间只留探测 |
| `api/emby_servers.refresh_mount_health` | 读旧快照 / 写新快照 + 提交夹在 HTTP 两侧 | HTTP 仍 await，读写快照合并成一个 `store()` 下放线程池 |
| `api/emby_servers.save_server` / `test_server` / `refresh_server_mounts` | 保存配置、写 `*_reachable`、同步清单、审计都在 `async` 体里 | 各自拆成嵌套同步函数；`get_servers` 体内没有 await，直接改同步 `def` |
| `api/servers.create_server` / `update_server` / `activate_server` / `refresh_mount_health_now` | 唯一性检查、落库、切换旧配置键、取当前 EA 都在 `async` 体里 | 同上；**提交之后要用的值都在工作线程里取成纯值**（`server_id` / `kind` / `url` / `realm_id`），不回循环上读 |
| `api/servers.emby_overview` | 整页读几十次库、按服汇总，全在 `async` 体里 | `load()`（范围 + 服 + 入口 + 探测目标）与 `build()`（组装）两段下放；只有节点身份探测在循环上 |
| `portal_mount_routes.check_all_mounts` / `test_saved_mount` / `browse_mount` | 取挂载行、写回结果、建 provider 都在 `async` 体里 | 探测仍 await（`test_mount` / `list_dir`），其余同步活儿在工作线程 |
| `realms.sync_realm_nodes`、`portal.verify_pan115_account` | 取服 / 取节点 / 取配置档与写回结论在 `async` 体里 | 同样拆开；体检后要展示的字段用 `node_facts()` 在工作线程里读 |
| `admin_core._audit` | 只接受管理员对象，隐含读 `admin.id` | **也接受主键整数**：提交会让 ORM 属性过期，async 端点提前把 id 取成纯值传进来，审计与其它写落同一个线程池任务 |

**为什么「提交后回读」值得专门处理**：`Session.commit()` 默认过期所有实例，之后哪怕只是
`server.url` 这样一次属性读取，也会在**事件循环**上发一条 SELECT。这类隐式回查不会让
`check_blocking_routes.py` 报红（它只认函数体里的 `db.xxx(`），但它在真机上就是「后台点一下、
别人卡一下」。所以工作线程里读、拿纯值回来，是这一版的一等要求。

验证（`scripts/smoke_test_backend_hot_paths.py` 第 5 节，进 CI）：给「这台机器写库就是慢」建模
（命中 `remote_servers` 的 UPDATE 先睡 0.35 秒），先自证测量方法有效（同样的 UPDATE 直接跑在
循环上 → 心跳空洞 **0.365s**），再走真实路由：

| 场景 | 心跳空洞 | 同时确认 |
| --- | --- | --- |
| 基线（体检落库跑在循环上） | 0.365 s | — |
| `POST /api/admin/servers/{id}/test` | **0.075 s** | `last_check_ok / last_check_message / last_checked_at` 真落库 |
| `POST /api/admin/emby/servers/mounts/refresh`（慢快照 0.35s） | **0.011 s** | 快照真写进 `SystemConfig`（挂载页读的就是它） |
| `POST /api/admin/servers/{id}/activate` | — | 服务器真被设为当前使用，且 `AdminLog.admin_user_id` 是这位管理员（=走通了 `_audit` 收整数那条路） |

阻塞路由基线：37 → **24**（`scripts/check_blocking_routes.py`）。

  媒体库里这类条目多时增量扫描的收益会变小。可以给「试过且没命中」记一个时间戳，
  按策略窗口再试（需要加列）。
- 清理阶段只在**来源可用**时遍历；目录 → guid 快照可以连那次游标读也省掉。
- **37 个 `async` 路由里仍在跑同步 SQLAlchemy**（v2.21.0 已把它钉成 CI 门禁，
  只减不增；v2.35.0 做掉两条热路径见二·八，v2.36.0 做掉两条求片链路 + 通知层见二·九；
  清单与「为什么不是机械改 `def`」见二·七）。剩下的主要卡在**探测层**
  （`backend/servers.py` 的 `probe_*` / `refresh_mount_health` 自己在 `async` 里查库）——
  要动就得连那一层一起拆。
- **筛选菜单缓存只在进程内**：`_FILTERS_CACHE` / 取值缓存都是每进程一份，多进程部署
  （当前是单 worker，见 `serve.py`）才会各自重建一次；单进程下不是问题。

### 已做掉：增量扫描 / 清理候选集 / 挂载缓存 / 图片本地化 / 扫描限速（v2.17.0）

这一版把清单上剩下的五项一次做完，核心都是**别做白工**。

**① 增量扫描（目录指纹）**。重扫一个库时，绝大多数目录一个文件都没动过，但旧实现照样把每个
文件走一遍完整流程（找图片、找字幕、重建外挂字幕轨、每文件一次提交）。现在按目录记指纹：

| 目录形态 | 指纹 |
| --- | --- |
| 本机（含 local / strm 挂载） | `目录 mtime_ns : 目录项数` |
| 远程挂载（115 / WebDAV / AList / 云盘） | `目录项数 : 总字节数` |

指纹没变 → 该目录的文件**不做任何写库工作**，只把 guid 记进 `seen_guids`（否则清理阶段会把
它们当「文件已删除」）并确认库里那一行存在且不需要重探/重刮/补详情。任一条不满足就退回完整处理。
指纹变了 → 整个目录照常处理，处理完写回新指纹。

跳过**永远**以「库里那一行存在且不过期」为前提，指纹只决定「图片/字幕/轨道这些逐文件的重活
要不要重做」：指纹写早了、随后进程崩了也不会漏文件——下次扫描会因为「查不到那一行」而重新处理。
替换同名文件不一定动目录 mtime，所以跳过的前提里还要求「文件大小与库里的记录一致」。

实测（2000 个文件 / 40 个目录，本机库，`scripts/_tmp_*` 之外的等价脚本已固化成 CI 用例）：

| 场景 | 耗时 | SQL 条数 | 逐文件处理次数 |
| --- | --- | --- | --- |
| 冷扫（建库） | 2486 ms | 8075 | 2000 |
| 未变动重扫（旧） | 2455 ms | 8034 | 2000 |
| **未变动重扫（现在）** | **144 ms** | **29** | **0** |
| 追新（+1 个文件） | 136 ms | 138 | 1 个目录（51 次） |

也就是未变动重扫从冷扫的 95% 降到 **6%**，且新增内容立刻入库（只重做它所在的那个目录）。
`SCAN_INCREMENTAL=0` 可整体关掉回到旧行为。没配 TMDB 的部署同样吃到增量：
刮削不可能成功时不该因此让整库每轮重做（配好密钥后的下一次扫描自然会重新处理这些条目）。

**② 清理阶段的候选集**。稳定库真正要遍历的只剩「行已存在但库里没这一行」以外的情形——
老实现每次都对整库条目做 ORM 游标遍历。现在先用两次计数证明「没有可清理的条目」
（`_no_removals_possible`，已有），退回遍历时也改成**只取 4 个列的 Core 游标 + 每批 5000 条**：
十万条目的稳定库从 2097 ms 降到 **37 ms**（同库 `COUNT(*)` 3.6 ms）；真需要遍历时
2226 ms → **569 ms**。逐行删除依旧显式带上 `UserMediaData`（无级联），不留孤儿行。

**③ 远程挂载目录列举下沉到 provider 层**。扫描方向本来有「本次扫描内只列一次」的缓存，
而**播放方向完全裸奔**：`resolve_play_target` 每次请求新建提供者，实例级 cid/pickcode 缓存
对播放等于不存在——115 上放一个 `/电影/2024/x.mkv` 要重新逐级列目录。现在缓存下沉到
`mounts.cached_listing`（九个提供者全部套上，含 115 的 raw 列表）：

- 按「挂载 + 配置指纹 + 方法 + 目录」做 TTL 缓存（`MOUNT_LIST_CACHE_SECONDS`，默认 30 秒），
  扫描与播放**共用同一份**；返回拷贝（调用方会排序/裁剪），**失败不缓存**（网络抖动不被固化），
  同一目录**单飞**（并发只请求一次，锁是可重入的——子类实现可能套在另一个被缓存的列举上）；
- 扫描开始前 `clear_dir_cache()` 会连这份缓存一起清（扫描必须看当下的目录）；
- `MOUNT_LIST_CACHE_MAX` 给内存封顶（满了整体清空）。

实测（假提供者计数）：两次播放（各自新建提供者）从 4 次网盘列举降到 **2 次**；
播放侧 `exists` + `size` + `exists` 三个问句只列 **1 次**目录；远程库重扫每目录仍然只列一次
（指纹复用遍历用过的那一份，不额外打网络）。后台目录选择器走 `list_dir_uncached` 看当下。

**④ 刮削图片本地化**。封面原先只有 TMDB 远程地址，客户端每取一次图都要由服务器代理去第三方
拉一趟。现在刮削时把图落一份到本地（`EMBY_IMAGE_DIR`，默认 `<EMBY_TRANSCODE_DIR>/images`），
远程地址**始终保留**：

- 缓存文件被清掉（/tmp 重启清空、维护淘汰、换过海报）都能**自愈**——取图时发现本地不在就
  按需再落一份并记住路径；落不下来就退回原来的代理路径，行为与本地化之前一致；
- 本地化过的图（在缓存目录里）优先走本地；**用户自己放进媒体目录的封面不受影响**（仍按原顺序）；
- 内容寻址（同图只落一份）+ 按 URL 单飞 + 「临时文件 → fsync → os.replace」原子落盘；
- 维护周期回收没被任何条目引用的文件，并按 `EMBY_IMAGE_CACHE_MB`（默认 2GB）从旧到新淘汰；
  **有引用的图一张都不删**（宁可超上限并记日志），新增文件有保护期（`EMBY_IMAGE_GRACE_SECONDS`）。

**⑤ 扫描限速**。POSIX 的 `nice` 是**进程级**的，而扫描跑在 API 进程的后台线程里——直接给本进程
降优先级会把正在播放的请求一起降，那是错的。所以只降**子进程**：ffprobe 是扫描里唯一的外部进程，
既最吃 CPU、也最容易和播放抢磁盘 IO。`SCAN_IO_NICE`（默认 10，0 关闭）给探测子进程加
`nice -n N`，能用的系统上同时用 `ionice -c2 -n7` 把 IO 降到 best-effort 最低档。
只在启动时探一次工具可用性（`ionice` 存在但内核不允许时不能挡住 ffprobe）：实测子进程运行时
`os.nice(0) == 10`、`ionice -p` 报 `best-effort: prio 7`，包装后 stdout/退出码照旧透传。

### 已做掉：逐集查剧集/季（v2.16.0）

写库循环原来对**每一集**点查两次（先剧集、再季）。现在 `_prepare_and_prefetch` 在批次开头
把这一批用到的剧集与季一次查回（`guid IN (...)`），并按 guid 缓存到本次扫描结束
（`_ScanContext.series_items` / `season_items`，存对象而不是 id，因为循环后段还要用它们做

**一次按 guid 的点查都没有**（`smoke_test_scan_budget.py` 用 SQLAlchemy 的
`before_cursor_execute` 事件数出来断言 `guid 点查 = 0`）。

同一版还把这个 1651 行的文件拆出了两个模块，扫描器只剩遍历与写库：

## 四、长期运行（跑几个月也不越跑越重）

扫描是「扫一次」的压力，长期运行还有另一类压力：**会随运行时间累积的东西**。
这些由 `backend/emby_server/maintenance.py`（看护线程）统一收尾，EM 与 EA 在启动时都会跑一遍，
之后每 `MAINTENANCE_INTERVAL` 秒（默认 600）跑一次：

| 会积累的东西 | 成因 | 收尾方式 |
| --- | --- | --- |
| `is_scanning` 停在 True | 进程被强杀（OOM / 重启 / kill -9），扫描标志来不及回写 | 启动时复位**真正残留**的；判定用「这次扫描什么时候开始的」，正在跑的绝不误清 |
| 播放会话永不结束 | 客户端异常退出，不会上报 Stopped | 心跳超过 10 分钟没更新就标记结束（结束时间用上次心跳） |
| HLS 转码目录 | 重启后注册表是空的，上一进程留下的分片再没人管（`/tmp` 是 tmpfs 时就是内存） | 启动时全清、此后只清「已停下且超过 5 分钟」的目录 |
| 字幕缓存 | 每个条目一份 VTT，只增不减 | 先删过期（默认 7 天），再按数量删最旧的（默认上限 2000 个） |
| 孤儿 ffmpeg | 父进程被 SIGTERM 时不会带走子进程 | 退出时统一终止在册的转码会话并清目录 |
| 播放进度/收藏的孤儿行 | `UserMediaData` 没有 ORM 级联，删条目不会带走它 | 扫描清理时显式一起删 |
| 限流桶 | 每个访问过的 IP 一个桶 | 超过 5000 个桶时清掉所有已过期的 |

播放会话（`emby_playback_sessions`）是这张表里唯一**故意保留历史**的：每播一次一行，
后台的「总播放次数 / 今日播放 / 一周热门 / 按日趋势」都靠它。默认不裁（历史统计口径不变）；
小机器想控制库体量可以设 `SESSION_RETENTION_DAYS=90`，看护线程会裁掉更早的**已结束**会话
（正在播的永远不碰），代价是统计只剩保留期内。

另外两件与「稳定」直接相关的事：

- **健康检查是常数级的**：`/api/health` 会报告转码会话数、正在扫描的库数、临时目录占用与磁盘余量；
  目录统计有硬上限（`REPORT_MAX_FILES`，默认 5000），残留再多也不会把探针拖慢，被截断时会标注
  `transcode_scan_truncated`。健康检查自身任何异常都只降级（返回空对象），不会变成 500。
- **删库与扫描互斥**：扫描中的库不允许删除（HTTP 409），删除改成分批（每批 500 条）——
  边扫边删会让已删除的库继续被插入条目，而 SQLite 会复用 rowid，新库撞上同一个 id 时那些
  条目会「复活」；分批则避免十万级库把面板拖死。扫描线程也会在批次边界发现库已删而提前收工。

可调环境变量：

| 变量 | 默认 | 作用 |
| --- | --- | --- |
| `MAINTENANCE_INTERVAL` | `600` | 看护线程周期（秒），最低 60 |
| `SCAN_STALE_HOURS` | `6` | 超过这个时长还没结束的扫描才算「残留」 |
| `SESSION_STALE_MINUTES` | `10` | 心跳超过这个时长就当作会话已结束 |
| `SUB_CACHE_MAX_FILES` | `2000` | 字幕缓存文件数上限 |
| `SUB_CACHE_MAX_DAYS` | `7` | 字幕缓存天数上限 |
| `REPORT_MAX_FILES` | `5000` | 健康检查里目录统计的上限 |
| `SESSION_RETENTION_DAYS` | `0` | 播放会话保留天数（`0` = 永久保留）。设成如 `90` 会裁掉更早的已结束会话 |
