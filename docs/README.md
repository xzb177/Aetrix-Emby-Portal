## 进阶：系统由两部分组成

整套系统由两个可分别部署的部分组成：

| | **EM · Emby Manager** | **EA · Emby API** |
| --- | --- | --- |
| 角色 | 运营面板 | Emby 协议网关 |
| 面向谁 | 浏览器（用户 / 管理员） | 播放器客户端（Infuse / Fileball / Forward+ / Hills / SenPlayer / 官方 App） |
| 管什么 | 注册 / 登录 / 套餐 / 续费 / 充值 / 邀请 / 卡码 / 签到 / 工单 / 风控 + 管理后台 | 只兑现协议：认证、媒体库浏览、拉流（302 直链）、字幕、进度上报 |
| 入口 | `python serve.py` | `python serve_emby.py` |
| 部署文档 | [deploy-em.md](./deploy-em.md) | [deploy-ea.md](./deploy-ea.md) |

**EM 是唯一事实来源**：用户、媒体库、套餐与订阅、设备上限、下载开关、限流口径都由 EM 写入共享数据库，EA 只读+回写播放态。因此 **EA 不能脱离 EM 单独运行**（缺共享密钥或共享库时会拒绝启动）。

也可以只跑 EM 一个进程（`ENABLE_EMBY_GATEWAY=true`，默认），由 EM 一并提供协议面——单机小站够用，上量后再拆。

**推荐拓扑：四个职责分开**（EM 控制面 / EA 数据面 / 独立 PostgreSQL / 统一媒体存储，内部全走私网）：
详见 [EA 网关部署 · 推荐拓扑](./deploy-ea.md#推荐拓扑四个职责分开)。
要点是**别让两台机器各自猜路径**：媒体来源一律用共享 WebDAV / rclone / 115 / AList，
否则会出现「面板扫描正常、播放节点找不到媒体」——后台的**播放可达性**会提前把这种库标出来。

**多服多机**（v2.6.20 起）：一个面板可以同时运营多个**服**（各自独立的媒体库 / 套餐 / 订阅 / 入口），
一个服也可以部署到多台机器上、多台 EA 同时出流。EA 用 `NODE_KEY` 认领自己那台机器、用 `REALM`
（或在面板里指定归属服）划定内容边界，会员按服判定。详见 [多台 EA 与多个服](./deploy-ea.md#10-多台-ea-与多个服多机多服)。

## 为什么两个服务都必须是单进程

`serve.py` 与 `serve_emby.py` 都固定 `workers=1`。HLS 转码的 ffmpeg 子进程管理与内存态会话都在进程内闭环，多 worker 会让"谁在转码、谁的会话还有效"分散到不同进程，出现重复 fork 与进程泄漏。**不要给任一个服务开多 worker**，横向扩展请按站点拆分。

## 与旧版拆分架构的关系

v2.0 之前的**旧拆分式**部署配置（`docker-compose.yml`、`deploy.sh`、`update.sh`、`user_backend/`、`admin_backend/` 等）**已从仓库删除**。它们与当前的 EM/EA 架构不共享数据库结构，留着只会让人误用；需要时从 git 历史取回（详见 [运维 · 排错](./operations.md#旧版拆分栈还在吗)）。
